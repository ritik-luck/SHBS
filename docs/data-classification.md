# Data Classification and Retention Policy

This document outlines the classification levels and retention requirements for operational and compliance data generated by the Self-Healing Backend System (SHBS).

## Classification Levels

1. **Internal (P0)**: System state data, ephemeral cache values, high-frequency metrics. Not considered sensitive but critical for operations.
2. **Confidential (P1)**: Business transactional data, incident reports, and PII. Requires strict access controls.
3. **Restricted (P2)**: Security audit logs, user credentials (hashed), API keys. Highest sensitivity and strict compliance constraints.

## Retention Matrix

| Data Type | Table / Datastore | Classification | Hot Storage (MySQL/Redis) | Cold Storage (S3 Archive) | Total Retention |
| :--- | :--- | :--- | :--- | :--- | :--- |
| Operational Metrics | `failure_metric`, `health_metric` | Internal | 30 Days | 60 Days | 90 Days |
| Incident Timelines | `incident` | Confidential | 1 Year | 5 Years | 6 Years |
| System Alerts | `alert` | Internal | 30 Days | 90 Days | 120 Days |
| Circuit Breaker State | `Redis (String/ZSet)` | Internal | 24 Hours | None | 24 Hours |
| Security Audit Logs | `audit_log` | Restricted | 1 Year | 7 Years | 8 Years |

## Archival Process
The `DataArchivalScheduler` uses a distributed `ShedLock` to ensure it only runs once per cluster. 
1. Every night at 3:00 AM, records exceeding the "Hot Storage" duration are selected in batches.
2. The batch is exported to a JSON file and uploaded to the `shbs-archive-bucket` in S3 (simulated locally).
3. The batch is then deleted from the hot datastore using timestamp-indexed SQL queries.

## Append-Only Policy
- The `audit_log` table restricts `UPDATE` and `DELETE` commands for the primary application user. 
- Modification of an audit record is technically impossible from within the application context.
